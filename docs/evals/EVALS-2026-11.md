## 3. The story

**How we write evals.** Evals start as contracts. Each is a small oracle with a committed case file:
164 evaluators and at least 2,069 cases. Most were written by an AI lane (Codex) that may write only to the
two eval directories, and a Claude lane reviewed and pushed its work (`docs/PRODUCT-BRAIN.md:46`). Codex
commits first added 191 of the 251 eval files and 156 of the 170 eval test files.
Every exclusion must ship with the mutation that would turn it red (ruling 087, `docs/rulings/087-an-exclusion-is-only-safe-where-a-mutation-can-red-it.md:7-10`).
A mutation result is reported as a split (what was killed here, what is owed to CI), never as a flattering
total (ruling 065, `docs/rulings/065-report-the-mutation-split.md:7-17`). For matching we keep a golden set:
709 market-to-event pairs adjudicated against production, replayed through the matcher's real SQL with
about six candidates each, so the test cannot simply agree with itself. For taste we built human-rating
harnesses, with a temporal holdout and rater agreement. They are waiting on labels: 24 single-card labels
with one positive, so the exam reads NO BASELINE MEASURABLE. For truth we keep a forward record: each
source's published prices, graded against what happened. It is published with a ledger of the calculations
we changed and the ones we chose not to change.

**How we use them.** The golden set and 1,137 eval test functions run in CI on every pull request that
touches the backend. The browser-audit contract fixtures and the search recall contract are required
checks the deploy waits on.
The golden set is also a floor that may not fall silently: since the 665-over-668 near miss (bite 2), the
required floor check refuses any drop that does not name every market that fell. Changes to numbers people
see, to matching or to settlement get
an independent Claude review that starts only once CI is green at that exact head. In its first afternoon
it requested changes 11 times: three were real defects, fixed before merge, and the other eight were
process holds that a same-day fix removed. And the 0.5 s meter puts a number on speed. It records each
venue's longest wait every minute, and on election night it posted the worst minute every hour. It counts
a minute it could not read as unknown rather than a pass, and judges each release against the 30 minutes
before it, with an automatic rollback.

**The clever part: we evaluate the evaluators.** The mutation batteries score the tests: 42 of them write
deliberate bugs into product code and expect a named guard to fail. The residue scanner keeps the batteries
honest. It exists because a killed run once left a mutant in a commit. CI runs it with the backend
suite, so a needle that drifts from its target fails the build. The browser-audit contract fixtures
mutate the audit rail itself, and they also exercise CI's own gates, including the AI reviewer's
wait-for-green script. If they stopped failing, every green the rail reports would be worthless. The bite-rate audit scores the evals: all 40 of its frozen
mutations bite, and the same audit pins the uncomfortable number, 0 of 40 cases on a real production type.
The meter's own false rollback on 11/03 became its test case: replayed against the corrected guard, that
morning's log now passes
([NOW](https://github.com/alexander-bain/bainluck/issues/11852#issuecomment-6613422935)). One limit,
stated plainly: the forward record grades the sources the blend is made of. Grading the blend itself, and
learning its weights from that record, is **aspirational** ([#11850](https://github.com/alexander-bain/bainluck/issues/11850)).
