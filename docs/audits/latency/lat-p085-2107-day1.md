## Why it is false — three independent reasons, none of them "the fix regressed"

The probe arm itself was **clean**: 59 samples, **zero 5xx**, all on commit
`b5c2a750`. Nothing the watch observed on `/api/feed` failed. The window was
disqualified three times over, and every one of the three is an instrument
defect rather than a finding about #2107.

### 1. The label made it ineligible before it started

`counts_as_day` was `(args.label == "day")`, and the window was launched
`--label LAT-P084-day1`. So `is_day=false` and `counts_toward_seven=false`
**regardless of the verdict** — the hour was spent on a window that could never
bank. This is gotcha #53's shape: a false `counts_toward_seven` collapses "the
fix regressed" and "the label was wrong" into one value, and a later reader has
no way to tell which they are looking at.

**Fixed** (`694f78b0`): `--counts-as-day` is now explicit, and the resolved
decision is printed *at launch*, before the hour is spent.

### 2. `restarted` was unconditionally true

`restarted = len(processes) > 1`. Production runs **one web dyno with
`WEB_CONCURRENCY=2`**, so two stable process ids answer every window — measured
2026-08-24 across eight back-to-back `/api/health` reads: `4211ad2cfb66` and
`c586a31af980`, both at uptime 6,701 s, climbing together. Day 1's own row shows
the same two ids with uptime **monotonically increasing** 4,690 → 4,770 → 5,153.
No worker restarted.

This is precisely the conflation **ruling 129** corrected, banked on this branch
four commits earlier at `79f1313b` — the watch simply predates it. The
consequence is severe and was invisible: **every window this deployment could
ever produce would grade INCONCLUSIVE, so the seven-day falsifier could never
bank a single day.** A broken falsifier that fails closed is indistinguishable
from a fix that has not yet proven itself, and "not yet closed" is the expected
reading, so nobody goes looking.

**Fixed** (`81e437c3`): `_detect_restart` uses `uptime_seconds` — already being
collected — and flags an uptime that goes *backwards* or a worker *born* during
the window. Verified live end-to-end (`--minutes 4` against production, 11/11
HTTP 200): `restarted: false`, `born_at_elapsed: -6806.4`, uptime 6,807 → 7,069.

### 3. The Sentry arm's 24 h lookback straddles the release — NOT fixed, see below

The FIRED verdict came from **one** BAINLUCK-ZK event
(`DetachedInstanceError: Instance <Team …> is not bound to a Session`,
"Feed pre-warm failed for sports"). Its timestamp:

```
event 84d667c45b68   2026-08-24T06:35:26Z
issue lastSeen       2026-08-24T06:35:26Z
fix deployed (v3886) 2026-08-24T17:23:50Z
```

**The event fired 10 h 48 m BEFORE the fix deployed**, and `lastSeen` says there
has been no event since. The probe arm measured the hour *after* the deploy; the
Sentry arm measured a fixed 24 h that is mostly *before* it.

This is exactly the hazard the directive named for item 1 — "a window that does
not straddle the release" — showing up inside the day-1 instrument. Structurally,
**on the first day after any deploy the Sentry arm necessarily includes up to 24 h
of pre-fix time, so day 1 can be failed by the very bug the deploy was shipped to
stop.**
