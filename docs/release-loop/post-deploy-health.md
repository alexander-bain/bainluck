## What runs

A signed Heroku `api:release` webhook is relayed by `/api/release-webhook` to GitHub `repository_dispatch` immediately on each successful main-app release. A successful master CI workflow and production Vercel `deployment_status` also trigger discovery. A five-minute scheduled reconciliation also checks the current provider release, including a Heroku release created outside GitHub. Receipts are GitHub deployments in `release-health-heroku` and `release-health-vercel`; the provider's immutable release/deployment ID makes repeated observations idempotent. The observer always checks out trusted master, never PR source with deployment secrets.

The worker probe and public routes run on a 30-second cadence with bounded requests. Boot health becomes available at three minutes; the existing worker check does not establish its final A10 verdict until the later scan+180 through scan+780 window. The observer retains that distinction and the original guard requirements instead of calling a three-minute startup pass a final latency pass. Public route exceptions, malformed JSON, a missing dependency reported by `/api/health`, and an empty or malformed feed fail the release. Vercel also requires the production website to return HTML.

The original watcher calls guard2 with `5000 10` and guard3 with `12 20 30`. Guard2 stops at two consecutive sampled minutes above 5,000 ms, excluding `na_orientation`. Guard3's executable code stops at three consecutive sampled minutes above 5,000 ms once the start+2-minute boundary is reached, and applies the 20-point deterioration rule to the under-500-ms minute share. Its docstring still says two; the executable code is authoritative. No threshold is inferred from HTTP request duration. The adapter reads `headline-clock` reports from worker logs and passes the original streak text shape to both original guards.

## Rollback and limits

`python3 tools/release/rollback.py --provider heroku --candidate-sha FULL_SHA --candidate-id RELEASE_UUID --reason REASON` is shared with the full-suite watchdog. Vercel uses `--provider vercel`. An optional `--previous-id` pins an already captured baseline. Without it, the entry selects the previous successful provider release with a different source SHA. An unknown source SHA or target refuses to mutate. A stale candidate never rolls back a newer release. Rollback is confirmed by a bounded 90-second read of the target source SHA before a success is reported. Successful rollback exits 1 so the watchdog remains visibly failed; a superseded candidate exits 0; an observer or rollback harness error exits 2. Like the old watcher, a 25-minute observation with no conclusive verdict stays UNKNOWN and exits 2; it does not invent a new latency rollback threshold.

The short rollback job owns `heroku-deploy`, the existing CI writer lock, or `vercel-production`. The 25-minute observer owns only its candidate observer lock and does not block deployments. Provider identity is checked twice before the rollback POST. **Heroku and Vercel do not supply an atomic compare-and-swap rollback against the current release.** The Actions lock excludes other Actions writers, but an independent external deploy in the gap between the last read and POST can still race. All autonomous release writers must adopt these writer locks after the Delivery Speed window finishes; this PR cannot promise transactional safety against an unrelated external deployer.

The provider API currently exposes the active production release, so five-minute reconciliation checks the current release, not an intermediate release already superseded before it ran. The authenticated Heroku relay and a preview-only provisioner are included. Activation requires server-only Vercel settings `HEROKU_RELEASE_WEBHOOK_SECRET` (at least 32 characters) and repository-scoped `RELEASE_DISPATCH_TOKEN` (GitHub contents-write permission for repository dispatch), then a Heroku webhook subscription. `python3 tools/release/prepare_webhook.py` previews; `--apply --master-is-current` is held until Alex confirms current master. Configure the secrets before the relay PR deploys, then verify actual signed Heroku payload and GitHub dispatch end to end. HMAC uses SHA-256 and constant-time comparison; only successful releases for `bainluck` are forwarded, only immutable release/event IDs leave the route, and non-2xx dispatch returns 503 so Heroku retries. Repeat events are idempotent at the observer receipt. Vercel's production GitHub deployment event supplies its immediate trigger; that integration also needs a live validation gate.
