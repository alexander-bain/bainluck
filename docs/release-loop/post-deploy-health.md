## What runs and what is trusted

Signed successful main-app Heroku release events relay to repository_dispatch. Each event consumes its **exact** release ID; a late, superseded release gets a receipt and one keyed NOW comment without changing current production. Vercel controlled promotion calls the observer directly, and production deployment_status plus five-minute reconciliation provide additional triggers. Receipts and NOW comments paginate beyond 100 rows; replay upserts the keyed comment.

Observers always check out trusted master. CI waiting and Vercel draft builds hold no production writer lock. Only promotion and rollback hold vercel-production; Heroku rollback shares existing heroku-deploy. Live Vercel identity is read from the actual bainluck.com alias, not a newer unpromoted draft.

The watchdog calls veto.py with --candidate-sha FULL_SHA --reason REASON **before** waiting for provider writer locks. Both providers receive a durable failed-source receipt even if that SHA is not live yet. Builders and promotions reject it. Promotion re-reads it immediately before domain assignment, and rollback re-reads the target's veto immediately before POST. Cached health PASS cannot override a later source veto. Rollback targets require provider-validated full-SHA PASS receipts; a successful platform build alone is insufficient. A failed or rolled-back source never becomes a fallback merely through another provider release ID, preventing oscillation.

rollback.py with --provider heroku|vercel --candidate-sha FULL_SHA --candidate-id ID --reason REASON is shared with the full-suite watchdog. It confirms the target source after mutation for up to 90 seconds. Exit 1 means confirmed rollback, 0 means superseded, and 2 means refusal/harness failure. APIs lack an atomic compare-and-swap rollback; the prepared Actions promotion path disables Vercel master Git automatic deployment and makes actual writers share their lock. Retire independent production writers before arming. Provider/API behavior remains a required live gate.

## Durable diagnostic input

The authenticated Heroku HTTPS drain enters Vercel /api/release-log-drain. Router-only frames stop there, avoiding recursive self-drain logging. Worker and Logplex-loss frames go only to the configured collector origin's /api/release-logs/drain, with private bearer authorization. The backend parses RFC5424 **octet-counted** frames into the exact UTC app[worker-ws]/heroku[worker-ws] shape consumed by unchanged check.py.

Redis retains only startup, gc/recovery, venue-minute/headline, error/crash diagnostics: **2 hours**, at most **5,000 lines × 2,048 bytes**. Credentials are redacted before persistence. Replay deduplicates. Source freshness uses the monotonic newest actual source frame, including ignored worker heartbeats; an old replay cannot refresh liveness. Truncation, rejected authenticated bodies, Logplex loss, stale source, and trimmed history make coverage incomplete. Reads require admin authorization. Parsing/storage run through to_thread and the existing bounded get_redis_client(); there is no database migration or heavy query. The health adapter consumes this persisted window and has no recent-1,500-lines fallback.
