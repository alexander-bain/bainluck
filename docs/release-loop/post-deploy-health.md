## What runs

A signed Heroku `api:release` webhook is relayed by `/api/release-webhook` to GitHub `repository_dispatch` immediately on each successful main-app release. A successful master CI workflow and production Vercel `deployment_status` also trigger discovery. A five-minute scheduled reconciliation also checks the current provider release, including a Heroku release created outside GitHub. Receipts are GitHub deployments in `release-health-heroku` and `release-health-vercel`; the provider's immutable release/deployment ID makes repeated observations idempotent. Each Heroku dispatch consumes its exact release ID, including an event that arrives after that release was superseded. The old release receives a SUPERSEDED receipt and one keyed NOW comment; replay updates that comment instead of posting duplicates. Receipts and NOW comments are paginated beyond 100 rows. The observer always checks out trusted master, never PR source with deployment secrets.

The worker probe and public routes run on a 30-second cadence with bounded requests. Boot health becomes available at three minutes; the existing worker check does not establish its final A10 verdict until the later scan+180 through scan+780 window. The observer retains that distinction and the original guard requirements instead of calling a three-minute startup pass a final latency pass. Public route exceptions, malformed JSON, a missing dependency reported by `/api/health`, and an empty or malformed feed fail the release. Vercel also requires the production website to return HTML.

The original watcher calls guard2 with `5000 10` and guard3 with `12 20 30`. Guard2 stops at two consecutive sampled minutes above 5,000 ms, excluding `na_orientation`. Guard3's executable code stops at three consecutive sampled minutes above 5,000 ms once the start+2-minute boundary is reached, and applies the 20-point deterioration rule to the under-500-ms minute share. Its docstring still says two; the executable code is authoritative. No threshold is inferred from HTTP request duration. The adapter reads `headline-clock` reports from worker logs and passes the original streak text shape to both original guards.

## Rollback and limits

`python3 tools/release/rollback.py --provider heroku --candidate-sha FULL_SHA --candidate-id RELEASE_UUID --reason REASON` is shared with the full-suite watchdog. Vercel uses `--provider vercel`. An optional `--previous-id` pins an already captured baseline. Without it, the entry selects a provider release with a durable health PASS receipt, validates its full source SHA against the provider, and excludes every source SHA that has ever received a failure or rollback receipt. An explicit target must meet the same requirements. A merely successful provider build is never a rollback baseline. Initial known-good baselines must be bootstrapped before arming; missing baselines refuse to roll back rather than oscillate between failed releases. An unknown source SHA or target refuses to mutate. A stale candidate never rolls back a newer release. Rollback is confirmed by a bounded 90-second read of the target source SHA before a success is reported. Successful rollback exits 1 so the watchdog remains visibly failed; a superseded candidate exits 0; an observer or rollback harness error exits 2. Like the old watcher, a 25-minute observation with no conclusive verdict stays UNKNOWN and exits 2; it does not invent a new latency rollback threshold.

The short rollback job owns `heroku-deploy`, the existing CI writer lock, or `vercel-production`. The 25-minute observer owns only its candidate observer lock and does not block deployments. Provider identity is checked twice before the rollback POST. **Heroku and Vercel do not supply an atomic compare-and-swap rollback against the current release.** The Actions lock excludes other Actions writers, but an independent external deploy in the gap between the last read and POST can still race. All autonomous release writers must adopt these writer locks after the Delivery Speed window finishes; this PR cannot promise transactional safety against an unrelated external deployer.

Five-minute reconciliation checks the current release as a fallback. The authenticated immediate provider event checks its exact release ID; a superseded release is recorded without probing or changing current production. The authenticated Heroku relay and a preview-only provisioner are included. Activation requires server-only Vercel settings `HEROKU_RELEASE_WEBHOOK_SECRET` (at least 32 characters) and repository-scoped `RELEASE_DISPATCH_TOKEN` (GitHub contents-write permission for repository dispatch), then a Heroku webhook subscription. `python3 tools/release/prepare_webhook.py` previews; `--apply --master-is-current` is held until Alex confirms current master. Configure the secrets before the relay PR deploys, then verify actual signed Heroku payload and GitHub dispatch end to end. HMAC uses SHA-256 and constant-time comparison; only successful releases for `bainluck` are forwarded, only immutable release/event IDs leave the route, and non-2xx dispatch returns 503 so Heroku retries. Repeat events are idempotent at the observer receipt. Vercel's production GitHub deployment event supplies its immediate trigger; that integration also needs a live validation gate.

## Vercel production control

Git automatic master deployment cannot participate in an Actions concurrency lock. This PR changes the existing `frontend/vercel.json` to disable only master Git deployments and adds `Vercel release`, controlled by the initially unset `RELEASE_LOOP_VERCEL_ENABLED` variable. Its workflow starts on master CI in-progress and completion events: a live-path candidate requires the actual selected-test step of `fast-gate` to have executed successfully, while other candidates wait for successful full CI. A skipped fast-gate is insufficient.

Waiting for CI and building the production-environment draft happen outside the production writer lock. The API draft request sets `autoAssignCustomDomains: false`, preserving production server secrets while keeping the live domain unchanged. Only the short promotion job and rollback hold `vercel-production`. The serving version is read from the actual `bainluck.com` alias, not merely the project's newest production-target draft. Promotion validates draft/source identity and source ancestry. Before activating this path, verify this project's root is `frontend`, the master Git deployment setting is honored, the no-domain-assignment API behavior is honored, and the promotion/rollback endpoints work on this account. These provider/API gates cannot be proved with internet disabled.

The full-suite watchdog must call `python3 tools/release/veto.py --candidate-sha FULL_SHA --reason 'live-path full-suite watchdog failed'` in its failure-recording job **before** waiting for provider writer locks. That writes a durable failed-source receipt for both providers even if neither has deployed that SHA yet. The production draft builder consults it, and the promotion job re-reads it immediately before changing the live domain. Thus a watchdog that fails while Vercel is building cannot return stale/SUPERSEDED and then allow that failed source to promote. Rollback also records the failure even when it is already superseded. Heroku deploy re-runs must consult the same failed-source set before releasing.
