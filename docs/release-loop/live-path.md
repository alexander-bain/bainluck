## What runs

The original change-scope script remains the full/frontend job classifier. The added selector admits the `live-path` label only for backend Python source/tests with direct test coverage and the canonical `tools/speed/` subtree. Requirements, migrations, app bootstrap/models/configuration, fixture hooks, unknown paths and deletions keep full CI. Backend selection follows direct imports, literal source reads and transitive test-helper consumers; it intentionally does not claim complete application impact coverage. The complete application suite runs after deploy. Pure moves/additions of speed tooling get startup plus Python/shell syntax and all `tools/speed/tests/test_*.py` tests that exist.

The `fast-gate` job has `timeout-minutes: 2`, including runner setup, checkout, dependency installation and tests. It pins Python 3.11, compiles Python with that interpreter, and folds in the PEP 701 check read from the existing speed tool. The deadline is a refusal on timeout. The scope and fixture jobs also have two-minute refusal deadlines. Queue time and the serial total have not been measured; this is an execution deadline, not a proven end-to-end hosted duration. A cold dependency install may use the whole allowance; this session could not measure hosted performance because internet is disabled.

A push must be one exact associated merged master PR carrying `live-path`; every associated PR must agree, and the classifier's base must equal the merge commit's first parent. A failed API lookup, a mixed push or a deployed-base gap uses full CI. The label and current PR head are fetched again from the API, including when an old run is rerun after the label changes. Scope outputs carry their producing run attempt. Fast gates, matrix markers, cheap required fixtures and deployment refuse retained outputs from another attempt and ask for a rerun of ALL jobs. Fast-gate and deployment fetch the newest trusted `release-loop-policy` deployment receipt and current PR metadata before proceeding; a stale successful scope cannot admit a label that was removed or a fast lane whose policy was disabled. The arming/disable tool writes the policy receipt (`authority: release-loop-policy-v1`, Boolean `fast_enabled`, full `master_sha`) before changing coarse repository variables. Runtime uses existing `deployments: read`, with no Variables API access or extra credential. The latest receipt wins even if it is disabled or malformed; older enabled receipts cannot revive it. Ordinary unarmed runs skip this verifier and retain full CI. Gate artifacts carry the exact run ID and attempt, and the watchdog validates both before interpreting the mode. Every matrix context remains expanded; successful marker jobs depend on the actual fast gate.

The post-deploy watchdog reads the exact CI run's recorded gate mode. Missing/invalid mode causes a full watchdog run. It checks out the deployed candidate SHA and runs the current eight backend shards, shard completeness, the database integration rails, the recall aggregate, frontend build/Jest/typecheck and browser contract fixtures. A parity guard requires its commands to remain identical to ordinary CI. Before waiting for a provider lock, it persists a failed-SHA veto for both providers. Promotion checks that veto under its writer lock, so a later Vercel promotion cannot undo a quick watchdog failure. The rollback matrix uses `heroku-deploy` or `vercel-production` concurrency for its provider and calls item 3's shared rollback CLI. Stale failures cannot rewind newer releases. Every Heroku push/retry path rechecks the durable source veto under its writer lock; a veto read failure refuses release.
