## Finding 1: missing retry after background history fills

Source pin: remote master `2d3dc8651d3aa620208016aa0d3f9da71f5d61ec`.

Confirmed code path: `backend/app/routes/futures.py:6945–6989` tries vetted venue history in Redis then durable Postgres; when both are cold, there is no venue series to add. Around 8445, thin/coarse capture data requests a background fill. `_plan_and_dispatch_generic_history_fill` (7045–7075) dispatches bounded work and returns `requested`; later requests can report `already_claimed`. `venue_history.describe` (6664–6693), included around 8852, exposes state, points served, build time, fill status and refusal metadata. A cold response serves the available stored-history path, not the forthcoming venue history.

The web page's SWR history fetch (`frontend/app/futures/[id]/page.tsx:225–240`) has no fill-aware retry interval and disables focus/reconnect revalidation. The response type (`frontend/lib/types.ts:1276–1294`) omits `venue_history`. **There is a missing completion retry, not a universal absence of subsequent requests:** the price-stream hook (`page.tsx:502`, `frontend/hooks/useFuturesDetailStream.ts:46–59`) can already invalidate/refetch history after quote changes. A quiet market can remain on its initially sparse response when filling finishes.

Retained measurements: first cohort requests were 17 cold / 3 refused / 1 warm. Thirteen cold pages later became warm, with request-to-build intervals 124–156s (median 139s). Twelve increased from 6–45 to 55–279 leading-outcome points; the guest page remained 10→10. The four separate timing-test pages extend the observed range to 99–219s. These are retrospective build timestamps during a request burst, not a general first-reader SLA or proof of how long a human stayed. The one-request-in-60s observation was on page 56775565, outside the cohort, transcribed without a retained network trace. Source review corroborates the missing fill-triggered retry.

Smallest recommendation, **not started**: type the existing venue metadata and add a market/range-bound retry only while filling is pending (`requested` / `already_claimed`), while visible. Keep the current chart; use genuinely fresh/no-store fetches with no hidden retry multiplication, roughly 20–30s spacing and a strict attempt/time ceiling that covers the observed ~219s fill (for example at most ten attempts over five minutes). Stop on completion, refusal/failure, hide/unmount/range change or cap; handle re-entry without concurrent loops. Preserve the backend's existing claim dedup and provider admission budget. Do not poll every sparse chart indefinitely. Cache semantics in `frontend/lib/api.ts:1045–1064` need to be exercised in tests; calling mutate alone does not prove a fresh network response.

Estimated effort: 1–2 engineering days including retry/cancellation/cache tests and bounded before/after rendering, conditional on safe file ownership and integration. Existing **#7547** owns generic history fetch/cache/reader (Live; UX/Native rendering compatibility), with **#883** as the landing-page parent. No new issue is needed. #7351 recovery and #7807 retention are already-built substrate, not permission to reopen them.

Discover prefill is larger: selected-market dispatch, quota/admission and completion tracking, spending provider work before any click. It may improve the first view but does not replace quiet-page completion retry and is not authorized here.
