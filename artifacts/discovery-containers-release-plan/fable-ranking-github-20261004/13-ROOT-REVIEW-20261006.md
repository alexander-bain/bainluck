## 3. Movers checks

### a. Same displayed quantity and same sources: NOT SATISFIED by the current Movers path

`backend/app/routes/futures.py:856` ranks outcomes by stored `abs(probability_change_24h)`; `movement_pool.py` bounds that query using its derivative `max_movement_24h`. Neither is a query over the displayed blend's history. The payload at line 965 uses `reader_change_24h`; that helper returns the stored per-write value for ordinary sources and the dated bank only for DataGolf. The query ranking remains per-write even in that exception.

The existing bank is `{outcome_id: [raw_price, observed_at]}` in market metadata (`futures_market_snapshot.py:1014`). The general producer requires exactly one snapshot bookmaker, an allowed identical-scale source (Kalshi, Polymarket or DataGolf model), and eligible price evidence. It does not store historical source membership/weights or the historical display-normalization denominator. Its gate is not a general same-composition blended-history contract. Discover's card reader already withholds raw deltas when display normalization changes their meaning; keep that protection. A `sources` list on today's card does not establish yesterday's contributors.

### b. Comparable timestamps: PARTIAL, insufficient for “since yesterday”

`dated_movement_points` subtracts an actual banked observation and independently accepts **12–24 hours** of age, then expires it. That is real progress, but it admits observations younger than the requested **20-hour minimum**. It is not a seven-day bank.

The Movers endpoint's `hours` parameter changes the cache key and echoed `timeframe_hours`; `_build_movers_query` receives no hours/window. Asking for 168 hours does not calculate a week's movement. Ordinary-source endpoint rows still carry per-write deltas. Do not label this as “since yesterday” or “this week”.
