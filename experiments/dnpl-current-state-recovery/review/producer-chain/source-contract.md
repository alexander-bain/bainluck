### Newer source differences that materially change reachability

1. **Observation-only previews are not persistence retries.** Current `_refresh_batch` can add `unobserved` or unchanged-but-complete observations to `preview_only`, skips their UPDATE, and invokes `propose(..., observation_only=True)`: [Live lines 3499–3506](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L3499), [3562–3594](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L3562). Current settlement preserves `preview_only` **and `unobserved`** instead of refusing them: [4553–4564](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4553). The older note saying unobserved settlement ends the chain applies only to a439. Do not infer a lock retry, a committed obligation, or quiet `refresh_pending()` republication for an observation-only preview.

2. **Observation-only admission needs strict complete freshness.** Current registry verifies a complete observation, a known stored time/value equal to the proposed rounded value, and eligibility. Missing/invalid or mismatched inputs call refusal. When the offered observation is no newer than stored and no prior pending exists, it returns without clearing an expired marker. An older periodic read may preserve a newer pending observation if value, contributor set, and vector dominance agree; it can still expire or stale-drop that state. A newer-than-stored offer with an existing pending source is ignored if the basis is incomplete, contributor set differs, any leg regresses, or the minimum observation does not advance. None of these ignored paths may allocate a fresh lease. A valid strictly newer observation reaches the ordinary pending replacement and must carry `prior.lease`, not open a new lifetime: [registry lines 421–492](../../producer-chain-metadata/reference/backend/app/utils/blend_preview.py#L421).

3. **The optional PM accepted-observation path validates twice and is intentionally disposable.** It validates candidate event identities before the read, reads without held-quote overlays within a 250 ms budget, verifies proven orientation and original immutable DB-clock bounds, and validates again at final preparation. It does not perform fallback orientation repair or add held quotes, stamp plans, history, or retry debt. See [Live lines 4385–4462](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4385). Those time budgets are bounds for selected work, not a guarantee of visible preview cadence or latency.

4. **`prepare_frames` must remain under the claim lock.** Current publisher acquires the connection and claims if necessary, then awaits `prepare_frames`, then serializes all resulting frames before its one EVAL: [Live lines 4654–4686](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4654). The optional callback performs final `validate` before any registry `expire` or `propose`; no allowed events means no registry mutation: [4464–4483](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4464). Moving proposal/metadata construction ahead of that validation would change authority and cancellation semantics. The ordinary pre-stamp path still composes before the publication call.

5. **Empty callback and empty batch are not identical.** `frames=[]` with no callback returns before claim. `frames=[]` with a callback can claim an epoch and then get no allowed frames; the connection is released normally, no publication is sent, and the claim is not undone. Final-validation rejection therefore means “no pending mutation/publication,” not necessarily “no owner claim.” See [4643–4668](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4643). The historical no-empty-claim assertion must be scoped to no callback.

6. **Claim/transport failure distinctions remain unchanged.** Current local epoch assignment is still only after claim `read_response` ([4573–4582](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4573)); a lost response remains uncertain. Known owner loss never reclaims, revokes still pass, serialization completes before send, and uncertain send/read/cancellation cleans up without replaying the preview batch ([4669–4703](../../producer-chain-metadata/reference/backend/app/tasks/live_blend_refresh.py#L4669)). A callback exception/cancellation now also enters that cleanup path. The callback may have mutated some registry state before throwing; source does not roll those mutations back, so the bridge cannot presume preparation failure means no state transition.

### Static assessment of the inspected candidate

The candidate follows the narrow source seam: an immutable `_ChainLease` is attached to the actual `_Pending`, preserved through `prior.lease`, allocated by a separate monotonic integer identity counter, and selected by oldest `(since, source)` during composition. This avoids receipt-time synthesis, object-identity churn, same-clock token collision, and reimplementing LiveBlendRefresher. A per-chain anchored absolute expiry with a conservative 1 ms reduction addresses the straightforward fractional truncation mismatch. Source clocks, price policy, pending sequence retirement, and current observation-only branches are otherwise intact in the shown patch.

`lease_id` is `pending:<counter>` rather than carrying the epoch itself. This is acceptable only while downstream identity is explicitly scoped by the real epoch (as the copied authority compares both owner epoch and chain); it is not globally unique across registry/process replacement. Reinitializing a registry under an unchanged epoch must not be treated as a supported production path.

Wall/monotonic and authority-clock alignment remain external prerequisites. The shown code samples wall at chain creation and uses later real wall values for issued stamps; it does not establish cross-process clock agreement or immunity to jumps. Multi-source leases opened across wall-clock jumps must not be advertised as proven to share a coherent absolute timeline. Invalid initial lease metadata remains absent for that lifetime, which is conservative live-only fallback rather than authority repair. No live retention transport was added by this registry patch; `retention_input.prepare` only builds a singleton command and expressly does not implement an atomic ordered batch.

## Findings that affect the seam

1. **A proposal sequence is not a chain identity.** `PreviewRegistry.propose` replaces `_Pending` on every accepted proposal, even for the same value, preserves the previous `since`, then records a newly composed sequence. This also preserves `since` when the value changes while still pending. A new value only necessarily opens a new lifetime after expiry has removed the old pending entry. See [pending state](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L188), [propose](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L419), and the explicit upstream changed-value countdown test at [test lines 349–360](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/tests/test_blend_preview_display_before_persist_195.py#L349). Value, basis, `seq`, `stamped_at`, and `_Pending` object identity are each insufficient as a stable chain key.

2. **The deadline is producer state, not transport receipt time.** `_compose` takes the oldest `since` among currently pending sources and emits `max(0, int((limit - (now - oldest)) * 1000))`: [lines 311–314](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L311). A queued batch has already spent some of that TTL. Adding TTL at dispatch, admission, or a later retry extends the lifetime. The metadata bridge must bind deadline and identity when the producer generates the frame, before the publication await.

3. **The three clocks must stay distinct.** `observed_basis` is the complete per-contributor observation vector: [aggregation lines 416–448](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/aggregation.py#L416). Each pending source's display clock is the oldest observation in its complete vector, and `display_observed_at` is the newest admitted source clock, requiring complete contributing clocks: [composition lines 317–353](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L317), [aggregation lines 1336–1362](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/aggregation.py#L1336). Legacy preview `observed_at` and `pending_entries.updated_at` are attempt stamps, not source observations. Neither can date chain creation or prove improved freshness. Missing/invalid display observations must remain unknown.

4. **Partial retirement can legitimately change the frame deadline.** Lifetime belongs to each pending source, not to an event-wide permanent lease. A sibling commit/refusal/expiry recomposes survivors using their unchanged `since`. Removing the oldest pending source can increase the remaining frame deadline without renewing any survivor: [committed/refused/expire lines 450–502](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L450), [upstream survivor-lifetime test](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/tests/test_blend_preview_195_review_guards.py#L449). A single composite identifier must not confuse that legitimate survivor deadline with renewal of the retired source.

5. **Retirement is not always a revoke.** Own commit removes a pending attempt if its proposal seq is not newer than the committing attempt; no pending sources means no emitted revoke. Newer same-source proposals survive an older attempt's commit. Sibling recomposition precedes committed frames; revokes follow them: [registry lines 465–477](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L465), [refresh lines 3827–3868](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L3827). A bridge that waits for an explicit revoke to forget every retired chain is wrong.

6. **Expiry markers prevent a quiet retry reopening the same expired value.** Expiry removes a pending source and remembers its current value; same-value proposals remain suppressed until a commit/refusal/different value clears the marker. Terminal status clears all pending/expired state; bounded event eviction may forget the marker: [lines 414–425](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L414), [479–512](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L479). Sidecar metadata must be bounded with the source state and distinguish a genuinely reopened chain, including a same-value chain after refusal or commit.

## Claim and publication failures: exact source behavior

### Claim lifecycle

- `epoch` starts as `None` ([registry initialization](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L226)). Frames may already be composed with that value before publication.
- Startup eagerly claims only for the selected preview arm. A process-local lock prevents simultaneous initial claims; known local epochs are reused: [claim_display lines 4455–4487](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4455).
- The claim script atomically increments the global counter and writes the source owner; the **local epoch is assigned only after `read_response()` returns**: [claim script](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L106), [claim call lines 4446–4449](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4446).
- Ordinary startup failure returns `None` and counts a publication error; a later nonempty publication retries the claim if local epoch is still `None`. An empty batch does not claim. A claim whose script ran but whose reply was lost is an uncertain result: local epoch remains `None`, so this source code may issue a fresh claim on a later call. Do not state unconditional exactly-once claim or strict process-start ordering after an unacknowledged initial claim.
- With a **known** epoch, a missing owner key or replacement owner is different: it fences blends and is not reclaimed by this process. The script permits revokes even from a non-owner: [fence script lines 113–121](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/utils/blend_preview.py#L113), [claim guard in publication](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4530). A reconnecting client is not a claim instruction; the adapter must not turn owner loss into a new lease/claim.
- Cancellation is not an ordinary swallowed failure. Inner cleanup catches `BaseException` and disconnects; outer handlers catch `Exception`, so task cancellation propagates. Preserve this lifecycle behavior rather than relying on the docstring's broad “never raises.”

### Preview batch transport

- `_preview_before_stamp` expires state, proposes all plans, records `pending_seq`, then awaits publication. The `published_seq` variable means **the attempt's sequence for settlement**, not a successful-publication receipt: [lines 4363–4395](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4363).
- `_publish_previews` holds one claim lock, borrows one connection, obtains an epoch if needed, stamps that epoch onto each frame, and JSON-serializes **the whole input batch before sending the one EVAL**: [lines 4521–4543](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4521). Replacing this with validate/send/wait per frame changes ordering and partial-failure semantics.
- The Lua script reads the owner once and visits the frames in supplied order. On its normal path it returns aggregate published/fenced counts plus owner, not per-frame receipts. Zero subscribers still does not establish browser delivery. This is no durable preview acknowledgement, and no retained preview recovery intent is created: [publication contract](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4496).
- An ordinary exception during serialization/send/read disconnects the borrowed connection, clears the cached Redis client, releases it, counts one publication error, and does **not retry this batch or roll back registry state**: [lines 4544–4565](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4544). A failure before send is unsent; a transport loss after send is uncertain. The adapter cannot treat every exception as “nothing applied,” renew a chain, or resend an uncertain whole batch automatically.
- Serialization failure in a later frame prevents this source's whole publish EVAL from being sent, although local frame epoch mutations and registry transitions may already have occurred. Do not silently publish a prefix while still claiming unchanged source semantics.
- The source has no transaction spanning registry mutations, Redis claim, Redis publication, and Postgres. Lua atomic isolation does not prove rollback of prior script effects on a runtime error. A new retained-authority batch needs its own explicit validation/partial-effect contract and negative tests; this source does not supply one.

### Database and ordered committed publication

- Readings are planned and previewed before event UPDATEs: [lines 3478–3500](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L3478). A lock timeout marks the event owed and preserves the preview: [3799–3816](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L3799), [4427–4431](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4427).
- A caught non-lock event failure is marked `preview_failed`; settlement later refuses it as `error`. No-group/unchanged/unobserved/stale/no-row outcomes also end that source's pending chain through refusal, subject to sibling recomposition: [3817–3819](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L3817), [settlement](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4397).
- A whole transaction/commit or setup failure exits before the post-commit settlement block. Pending preview state is not automatically refused or renewed; the outer refresher queues owed work, with normal failure hold or immediate existing lock retries: [singleton failure handling](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L2127), [failed-work retention](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L2440), [post-commit boundary](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L3827). TTL continues to run while retry work is delayed.
- Normal committed publication uses its own bounded packed commands, drains per-command errors, and acknowledges only positively confirmed revisions. Unknown transport state is disconnected and not retried within the attempt: [lines 4250–4359](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4250). Preview admission is not that committed acknowledgement and must not pay committed recovery debt.
- Preserve `recomposed preview -> committed frames -> revokes` even if a phase is empty. A failed ordinary committed publication is swallowed by the committed publisher while retaining recovery debt; it does not reverse the database commit or revive the old producer chain: [4084–4117](https://github.com/alexander-bain/bainluck/blob/a43949050b966b8009bddd5dda1afd65ddf1f9f6/backend/app/tasks/live_blend_refresh.py#L4084).

## Minimum safe metadata seam

Prefer a small **producer-registry lifecycle seam**, not a reimplementation of LiveBlendRefresher and not a frame-receipt heuristic:

1. Allocate a unique per-source chain token when an admitted pending lifetime is actually opened. Preserve it, the original monotonic deadline, and a fixed wall/monotonic mapping across pending-entry replacement and all compositions. Retire that token only when the corresponding pending lifetime really ends. Neither `since` equality nor identical value/basis is a unique token: distinct lifetimes can begin at the same injected clock, and object identity changes on every re-proposal.
2. At composition, snapshot the contributing source tokens and their original deadlines. For the current single-source canary, that token is the frame lease identity. For multiple sources, use an unambiguous composite identity or the controlling earliest-deadline token with a deterministic tie-break; if the controlling source retires, survivor identity/deadline must still be tied to its preexisting lifetime. Always use the earliest original deadline among current contributors.
3. Keep a token epoch-independent until the real claim is known, then namespace offered identity with the actual claim epoch. Never invent epoch zero as successful ownership and never bind permanently to `None` at first proposal. A known-but-fenced epoch remains fenced.
4. Capture the producer-issued timestamp and original absolute expiry before any enqueue/publication await. Use an explicit, testable monotonic-to-wall mapping; do not use contributor observations or attempt timestamps as a proxy. Do not recompute original expiry using a later receipt's clock. State clock-sync/skew assumptions separately from the producer lease proof.
5. Account for rounding: unchanged source TTL truncates fractional milliseconds. Independently flooring issued time and expiry can make `original_expiry > issued + ttl` by 1 ms and send a valid candidate to uncached fallback. Test fractional starts/retries explicitly and choose conservative mapping/rounding that never extends original lifetime. Do not “repair” this by increasing original expiry or refreshing TTL at dispatch.
6. Snapshot/deep-copy metadata with the frame. Subsequent registry mutation, settlement, or owner transition must not rewrite an already queued frame's lifetime. Missing/invalid metadata must take the documented uncached fail-closed path, not synthesize retention authority.
7. Keep batch command construction distinct from dispatch. Validate/build the entire ordered candidate batch before sending; preserve known-unsent versus acknowledged versus uncertain outcomes. Any departure from one-script preview semantics needs a stated contract and tests, not an assertion of unchanged behavior.

## Precise offline reachability tests

These are required tests/review targets, not claimed executions. Import actual pinned methods and inject only time, SQL outcomes, connection protocol, and candidate metadata seam; prohibit socket creation. Do not duplicate the refresher implementation.

- **Quiet no-input retry:** call actual `refresh_pending()` after a locked first `refresh`; assert zero new venue input, increasing seq and attempt clocks, unchanged observed basis/display clock, unchanged chain identity/original expiry, and decreasing TTL. Timings are fixture choices, not a global 2 s guarantee. Include a delayed publication queue and verify queue delay is not added back.
- **Changed value while pending:** propose A then B before expiry; identity/deadline remain the same. After expiry of B, a retry of B emits no blend; a different value A may open a genuinely new token/deadline.
- **Same time, different lifetimes:** refuse or commit then re-propose at the exact same fake monotonic instant with the same value/basis. The new chain must not collide with the retired one. Include eviction/recreation and terminal/reopen.
- **Sibling removal:** stagger two source chain starts, then independently commit/refuse/expire the oldest. Survivor token/deadline stays unchanged; its later deadline is not mistaken for old-chain renewal. Exercise stale elimination against a newer base as well as explicit refusal.
- **Older commit versus newer proposal:** capture attempt seq A, propose seq B, settle A; B survives with original chain metadata. Settle B; no pending source remains and no revoke is required. Verify metadata sidecar is retired despite absent revoke.
- **No initial epoch:** compose before claim; accepted command uses the actual later claimed epoch and correct preclaim deadline. Empty batch must not claim. Claim known failure before execution may retry on the next call. Claim effect with lost reply must be reported uncertain; do not count it as confirmed owner or an ordinary missing-owner case.
- **Known owner loss/replacement:** retain local epoch, remove/replace owner, offer blend plus revoke. Assert no claim call, blend fenced, revoke allowed, and no deadline renewal. This can be tested with an in-memory protocol model but is not Redis execution evidence.
- **All-before-send validation:** make the second frame non-serializable or metadata-invalid and inspect the candidate's intended failure contract. If preserving source all-or-none pre-send behavior, no EVAL may have been submitted. Do not allow an unreported published prefix.
- **Send/read failures:** separately inject before-send failure, send accepted with lost reply, first response acknowledged then later response error/transport loss in a packed candidate batch, and cancellation. Assert no automatic retry of uncertain commands, connection disconnection/release as appropriate, registry lifetimes not reset, and retained/committed acknowledgement not inferred from an offer being queued.
- **Database commit failure:** propose successfully, allow UPDATE RETURNING, then raise on transaction exit. Assert no committed output or false pending retirement, source work remains owed, retry retains chain/deadline, and expiry can still occur before the next attempt.
- **Per-event error versus lock:** same pre-stamp publication, then one lock failure and one ordinary failed event. Lock preserves pending; ordinary error refuses/recomposes/revokes. Missing group and refusal clear expired markers too.
- **Post-commit phase order:** use actual `_refresh_batch`/`_preview_settlement`; record recomposed blend, commit, revoke order. Fail committed publication and verify chain retirement still reflects SQL success, with committed recovery debt separate from preview retention.
- **Clock edge cases:** fractional milliseconds, a long pre-publication pause, wall-clock backward/forward jumps, absent/incomplete/invalid basis, and different contributor clocks. No metadata path may relabel attempt time as an observation or extend original expiry after receipt.
